Evolution API vs Evolution GO

Duas APIs de WhatsApp da mesma fundação, com propósitos diferentes. Uma prioriza alcance de recursos; a outra, custo de infraestrutura. Este deck mostra o que muda na prática — e a stack ao lado sobe as duas juntas, para você comparar com a mesma carga.

Evolution API
Node.js + TypeScript · Baileys · v2.3.7 · Apache 2.0
  • Canal Baileys (WhatsApp Web) e Cloud API oficial da Meta
  • Integrações prontas: Typebot, Chatwoot, Dify, n8n, OpenAI
  • Manager web embutido, sem licença para usar
Evolution GO
Go + whatsmeow · v0.7.2 · Apache 2.0 + proteção de marca
  • Binário compilado: boot sub-segundo, RAM em outra ordem de grandeza
  • Só WhatsApp Web (whatsmeow), sem integrações embutidas
  • Exige licença ativada — sem ela, 503 em tudo
A diferença em uma frase
Evolution API

Mais recurso
por instância

Plataforma de mensageria: fala WhatsApp Web e Cloud API oficial, e traz chatbot, CRM, filas e storage plugáveis por variável de ambiente. Você liga o que precisa sem escrever cola.

Evolution GO

Mais instância
por servidor

Motor enxuto: faz o essencial (conectar, enviar, receber, emitir evento) gastando uma fração dos recursos. A inteligência fica no seu sistema, não na API.

Não é "melhor" e "pior". A pergunta certa é: o gargalo do seu projeto é funcionalidade que falta ou servidor que não aguenta?

A API na prática

Autenticação: a pegadinha que mais confunde

As duas usam o header apikey, mas com modelos opostos. Trocar um pelo outro devolve 401 sem explicação.

Instância na URL
a chave é sempre a GLOBAL
# criar
POST /instance/create
  apikey: GLOBAL
  {"instanceName":"teste"}

# QR / status / envio
GET  /instance/connect/teste
GET  /instance/connectionState/teste
POST /message/sendText/teste
  apikey: GLOBAL
  {"number":"55...","text":"oi"}

Uma chave abre tudo. Simples de operar — e, por isso mesmo, perigosa de vazar.

Instância no token
a GLOBAL só cria e apaga
# criar (única rota com a global)
POST /instance/create
  apikey: GLOBAL
  {"name":"teste","token":"..."}
  -> devolve data.id + data.token

# daqui pra frente: token da INSTÂNCIA
POST /instance/connect
GET  /instance/qr
POST /send/text
  apikey: TOKEN DA INSTÂNCIA
  (sem id na URL)

Cada instância tem a própria credencial. Vazou uma, o estrago para nela.

Assimetria a decorar no EvoGo: DELETE /instance/logout usa o token da instância; DELETE /instance/delete/{id} usa a chave global.
Operação

A licença do Evolution GO

O item que mais gera chamado de "subiu mas não funciona". Não é falha da stack: é o produto se protegendo.

Como se comporta
  • 503 em todas as rotas até a licença ser ativada
  • Ativação pelo Manager web + heartbeat periódico
  • Estado gravado no banco evogo_auth
  • Com EVOLUTION_OPERATOR_EMAIL, os boots seguintes reativam sem navegador
A armadilha do Docker

O hardware-id da licença deriva do hostname do contêiner. Sem fixar, o Docker sorteia um hostname novo a cada recreate — e a licença enxerga "outra máquina" toda vez. Resultado: reativação a cada boot, até estourar o limite de ativações. 

services:
  evogo:
    hostname: evogo   # não remova

A Evolution API não tem nada disso: sobe e responde na hora.

Decisão

Qual escolher

Regra prática, sem torcida.

Evolution API se...
  • Precisa do número oficial (Cloud API da Meta), não só do QR
  • Quer Typebot / Chatwoot / n8n / OpenAI ligados por variável, sem código
  • Quer o ecossistema maior: mais material, mais gente usando, mais exemplo pronto
  • Não quer depender de ativação de licença
Evolution GO se...
  • Vai rodar muitas sessões por servidor e a conta de infra pesa
  • Seu sistema já tem bot, CRM e automação — só falta o transporte
  • Quer reinício rápido e footprint previsível (boot sub-segundo)
  • Precisa de pareamento por passkey em contas que exigem WebAuthn
Não é escolha exclusiva: dá para as duas conviverem no mesmo servidor, com o mesmo Postgres. Muita operação roda a Evolution API onde precisa de Cloud API e o EvoGo no volume de QR.
Passo a passo

Subir no Docker Desktop

Windows ou Mac, do zero, em cinco passos — nada precisa ser compilado.

  1. Docker Desktop aberto e rodando — baleia na bandeja com status Engine running (no Windows, WSL2 ativo). Deixe ~2 GB de RAM livres.
  2. Descompacte o evo-evogo.zip e abra o terminal dentro da pasta. 
    cd evo-evogo
  3. Crie o arquivo de variáveis e preencha os três segredos. 
    cp .env.evo-evogo.example .env.evo-evogo
openssl rand -hex 32   # rode 3x: PG_PASSWORD, EVO_GLOBAL_KEY, EVOGO_GLOBAL_KEY
    No PowerShell, sem depender de openssl (também 3x): $b=[byte[]]::new(32);[Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b);($b|%{$_.ToString('x2')}) -join ''
  4. Suba a stack. A primeira vez baixa as imagens (alguns minutos). 
    docker compose -f docker-compose.evo-evogo.yml --env-file .env.evo-evogo up -d
  5. Confira no Docker Desktop → aba Containers: o grupo zpro-evo com 5 serviços. db-init fica Exited (0) — é o esperado, ele cria os bancos e sai. Clique nas portas em Port(s) para abrir no navegador.
Só o EvoGo pede mais um passo: abra 127.0.0.1:18082/manager/login e ative a licença (até lá ele responde 503). Depois ponha o mesmo e-mail em EVOLUTION_OPERATOR_EMAIL e rode up -d evogo — dos próximos boots em diante ele reativa sozinho.
